## Decision 1 — Token: vaulted Account API token; OIDC for CI

- **Account API token, not user token** (Cloudflare-recommended for service use), with
  **TTL + client IP filtering** (Cloudflare's restriction guidance), vaulted (never
  shell-profile/`.env`), rotated 30–90 days.
- **CI uses OIDC federation** — officially supported since late 2024
  (wrangler-action@v3), `id-token: write` required, silent-failure risk if
  misconfigured. `publish-canon.yml` is already wired for OIDC with
  `permissions: id-token: write`.
- **Bootstrap:** parent token created once in the dashboard, used to mint the Account
  token, then locked to token-creation only (Cloudflare "highly recommends" no extra
  perms on the minting token).
- **Two lifecycles:** API tokens rotate on *your* schedule; Cloudflare Access service
  tokens expire **silently** at 8760h — monitor with a notification policy, don't
  rely on rotation.

edits `deploy/.well-known/did.json` thinking it's live, and the DID document silently
rots.

**Fix: delete `deploy/` entirely.** The source of truth is `public/`:

```bash

```

## The actual #1 blocker: npm bootstrap sequence

The blocker is **no package exists yet + npm credential 401** — not canon TS. The
sequence:

1. **Create a granular npm token** with publish scope for the `@p31` org
   (`npm token create --publish`, or npm web UI).
2. **Publish each package once with `--provenance`.** Provenance is **not**
   OIDC-dependent — the Sigstore attestation is generated by the npm CLI on any
   publish with a valid credential. A token-based first publish ships a
   provenance-signed tarball.
3. **Register the trusted publisher per package** (npm → package → Settings →
   Publishing access → add repo + workflow). This unlocks OIDC for publishes 2..n.
4. Subsequent publishes use the already-wired `publish-canon.yml`
   (`id-token: write`, trusted publishing).

**Correction to earlier framing:** the private repo is **not** the blocker for OIDC
first publish — the blocker is that the package doesn't exist yet. OIDC trusted
publishing works fine from private repos once the package exists.

## Version-pinning footgun (`workspace:*`)

`@p31ca/governance` declares `"@p31ca/design-core": "workspace:*"`. pnpm substitutes the
local version at pack time. If governance is packed before design-core 2.2.0 exists in
the workspace, the tarball ships `"@p31ca/design-core": "2.1.0"` — and the facade
resolves to a design-core that lacks `./governance`. Silent breakage.

**Fix (CI gate):** after each pack, verify the published tarball's dependency floor:

```bash
npm pack --dry-run --json | jq '.[0].files[] | select(.path=="package.json")'
npm view @p31ca/governance dependencies.@p31ca/design-core
```

The published value must be `^2.2.0`, not `2.1.0`.
